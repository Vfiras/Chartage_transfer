# Security Architecture — Carthage Transfer

*Draft for review. Written from the project's actual implementation (FastAPI + MongoDB
backend, Flutter client, LangGraph-based AVA assistant). Section references point at the
real modules so claims can be checked against code.*

---

## 1. Authentication

- **JWT bearer tokens.** Login (`POST /api/v1/auth/login`, `app/api/v1/endpoints/auth.py`)
  validates credentials against the `users` collection and returns a signed token via
  `build_token_response`. Token settings live in `app/core/config.py`:
  `jwt_secret_key` (required, no default — must be set in `.env`), `jwt_algorithm = HS256`,
  `access_token_expire_minutes = 7 days`.
- **Server-side enforcement.** Protected endpoints depend on `get_current_user`
  (decodes/validates the token and loads the user); admin-only analytics use `require_admin`.
- **Client-side handling.** The Flutter `AuthService` stores the token, exposes
  `isAuthenticated`, and injects it into every request through `TransportApiClient.setToken`.
  The AVA chat transport (`assistant_api_service.dart`) attaches `Authorization: Bearer <token>`
  on the SSE `POST /assistant/chat` call.

## 2. Authorization / role model

- **Two roles:** `client` and `admin` (`UserModel.role`). The role travels in the JWT and is
  read back server-side as `current_user["role"]`.
- **AVA role gate.** The assistant endpoint derives the role from the authenticated user, not
  from anything the client sends. The supervisor's `role_gate_node`
  (`app/ai/supervisor.py`) blocks a `client` from ever reaching the admin-only domains
  (`operations`, `insights`) and returns a polite refusal **without dispatching any tool**.
  Every denial is written to `audit_log` (`event: access_denied`) with user id, role and
  attempted domain — an audit trail of privilege-boundary hits.
- **The role gate cannot be bypassed from the prompt.** Because access is keyed on the JWT's
  role (server-derived), a client cannot talk their way into Operations/Insights; the gate
  fires before dispatch. This was verified directly (test_supervisor_cli "client → admin domain"
  → refusal + audit entry).

## 3. Per-user data scoping

- Tools are bound to the caller's identity in `tool_registry.get_tools_for_role(role, user_id)`:
  the `user_id` is pre-bound into each tool, so e.g. `get_trip_history` can only ever return the
  authenticated user's trips. The model never supplies the `user_id` — it is injected from the
  session, so a user cannot request another user's data by manipulating arguments.
- The tool set itself is role-filtered: client agents only receive client tools; admin agents
  only receive admin tools.

## 4. The confirmation gate (write-action safety)

- All state-changing tools (create/update/cancel booking, submit complaint, fleet/pricing/
  supplier/promotion writes, booking-status changes) go through
  `run_with_confirmation` (`app/ai/agents/shared.py`): the action is **proposed** in plain
  language ("I'd like to … Reply **yes** to confirm or **no** to cancel") and only executed
  after an explicit affirmation. This prevents the model from silently mutating data.
- Confirmation copy is generated by hardcoded templates (`format_tool_summary`,
  `humanize_result`) that never expose tool names, raw JSON, argument keys, or `null` —
  guarded by a deterministic test (persona-leak Section 3).
- **Read-only actions are deliberately *not* gated** (June 2026 fix): fleet/pricing/supplier/
  promotion *list/get* execute immediately and their data is synthesised back to the admin,
  rather than being hidden behind a confirm step. (See bug-fix log §"Read-only admin gating".)

## 5. Output-safety guards (preventing internal leakage)

- **Persona prompt.** Every user-facing model call runs with `AVA_PERSONA_PROMPT`, whose
  strict rules forbid revealing tool names, function/parameter/field names, code blocks, or raw
  JSON, and forbid stating specific named facts not present in the retrieved context. This
  closed a real "assistant talks like a developer and leaks `get_trip_history`/`_id`/`user_id`/
  ```` ``` ```` " bug.
- **`extract_text`** flattens model responses and strips structured/reasoning blocks (e.g.
  Gemini's block list with `signature`/`extras`), so only visible prose reaches the user.
- **Safety check.** `safety_check_node` cross-checks success-claiming language ("done",
  "confirmed", "cancelled", …) against actual tool evidence (a `ToolMessage`); if the model
  claims success without a tool having run, the claim is overridden — preventing fabricated
  "Done!" confirmations.

## 6. RAG faithfulness controls

- Support answers are grounded in a Chroma vector store built from `app/ai/knowledge/*.txt`.
- **Relevance floor (0.25).** `search_knowledge_base` drops chunks below the floor and returns
  empty context when nothing clears it, so questions the KB does not cover trigger an honest
  "I don't have that specific detail" instead of a confident hallucination. The floor was
  chosen from observed scores (on-topic answers ~0.36–0.57; absent topics ~0.10–0.13).
- **Index-staleness guard.** Each vector-store build records `source_manifest.json`
  (per-file SHA-256); `log_freshness_on_startup()` warns loudly at backend startup if any
  knowledge file changed since the index was last built — closing the gap that once let a
  stale index serve invented policy figures.

## 7. Three-tier model routing (and its security-relevant properties)

`app/ai/model_router.py` selects a tier on two independent axes:
- **Privilege axis:** any `admin` task → `CLOUD_PRIMARY` (Gemini).
- **Complexity axis:** client *synthesis* → `CLOUD_PRIMARY`; client classification / lookup /
  RAG retrieval / disambiguation → `LOCAL_MODEL` (Ollama `llama3.1:8b`).
- These are kept as distinct branches so a future change to one cannot silently move the other.
- Graceful degradation: synthesis falls back to LOCAL (or a deterministic template for
  loyalty/vehicle) if the cloud tier is unavailable, so an outage degrades quality rather than
  breaking the response. The cloud free tier is rate-limited (confirmed 20 requests/day via a
  live `429 RESOURCE_EXHAUSTED`), which the fallback path handles.

## 8. Secrets management

- **No secrets in committed source.** `GOOGLE_API_KEY` (Gemini) lives in `backend/.env`
  (gitignored). The Google Maps key lives in `android/local.properties` (gitignored) and is
  injected into the Android manifest at build time via a gradle `manifestPlaceholder` — it is
  **not** hardcoded in the committed `AndroidManifest.xml`.
- `Settings` (`app/core/config.py`) uses pydantic-settings with `extra = forbid`, so an
  unknown/typo'd env var fails fast rather than being silently ignored. (Every key the app
  uses is declared, including `maps_api_key`.)

## 9. Known gaps / honest caveats (for the report's "future work")

- The Maps "route line" is a straight connector, not real road routing (Directions API not
  wired), and pickup/destination markers resolve only for a curated set of known Tunisian
  places (the booking/destination models still store address strings, no lat/lng).
- Release builds currently sign with the debug key (`android/app/build.gradle.kts` TODO) — a
  real signing config is needed before distribution.
- Rate limiting / abuse protection on the public API is not covered here and is worth a pass.
